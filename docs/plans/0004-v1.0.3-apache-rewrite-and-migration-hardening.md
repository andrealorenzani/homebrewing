> Ship version 1.0.3: fix a production-blocking bug found during the user's first real deploy to shared hosting (Apache), plus a related hardening improvement discussed earlier.
>
> Bug 1 (urgent, confirmed live on the user's site): apps/web/public/index.php is a front controller meant to handle every request, but apps/web/public/ has no .htaccess. On Apache (the real production environment — DreamHost in this case, though the README must stay host-agnostic per existing convention), unmatched URLs like /register and /login return a raw Apache 404 instead of reaching the router, because Apache has no built-in fallback-to-index.php behavior the way PHP's `php -S` dev server does (confirmed by testing locally: `php -S` happily routes /register through index.php with no router script needed, which is exactly why this gap was never caught by local testing or the existing test suite — it's an Apache-specific gap, not a PHP application bug). The homepage ("/") worked because Apache's DirectoryIndex serves index.php for a bare directory request, but nothing else does.
>
> Required fix: add `apps/web/public/.htaccess` with a standard front-controller rewrite (serve real files/directories directly — including the existing public/css/ assets — and route everything else through index.php). Suggested rule set (verify/adjust as needed, e.g. for correctness with query strings and the existing routes):
>
>     RewriteEngine On
>     RewriteCond %{REQUEST_FILENAME} -f [OR]
>     RewriteCond %{REQUEST_FILENAME} -d
>     RewriteRule ^ - [L]
>     RewriteRule ^ index.php [L]
>
> Verify this actually works against real Apache, not just reasoned about — this repo already has Docker available (used for MySQL and PHP-with-extensions testing in prior rounds); spin up a throwaway Apache+PHP-FPM or apache2+mod_php container serving apps/web/public with this .htaccess and curl a non-root route (e.g. /healthz or /login) end to end to confirm a real Apache actually honors it (AllowOverride must be enabled in that test container's config — note in the plan if a real shared host has AllowOverride disabled by default, this could still fail there, and document that risk/fallback in the README). Also update index.php's own comment (currently says "a future .htaccess rewrite" — that future has arrived, fix the comment) and the README's deployment section to mention this file exists and is required for Apache-based hosts (i.e. most shared hosting), including a one-line troubleshooting note for exactly the symptom the user hit (homepage loads, every other route 404s) in case someone else's host has AllowOverride disabled and needs to ask their host to enable it or add the equivalent to a main vhost config.
>
> Bug 2 / hardening (previously discussed with the user, not yet built — the user has not explicitly confirmed they want this, so use your judgment on inclusion but lean toward including it since it's small, safe, and directly informed by a second real incident on the same live deployment): the user separately hit `PDOException: SQLSTATE[42S22]: Column not found: 1054 Unknown column 'version' in 'field list'` when running migrations against a shared/reused MySQL database that already had an incompatible pre-existing `schema_migrations` table from another application (this app's `MigrationRunner::ensureMigrationsTableExists()` uses `CREATE TABLE IF NOT EXISTS`, which silently no-ops against a same-named-but-differently-shaped existing table). Add a defensive check: when `appliedVersions()` (or migrate()) hits a database error querying `schema_migrations`, catch it and re-throw a clear, actionable exception explaining that a `schema_migrations` table already exists with an incompatible structure, that this usually means the configured database is shared with another application, and that this app requires a dedicated database. Do not attempt to auto-fix or auto-migrate the foreign table — surface the problem loudly and safely, nothing destructive. Cover this with a unit test against `FakeDb` or a small real-PDO-exception-shaped test double, whichever fits the existing test patterns in `apps/web/tests/Unit/Db/MigrationRunnerTest.php`.
>
