# Plan: v1.0.4 — Recipe Form Simplification + TO_BE_DONE.md Cleanup + deploy.sh Relocation

**Status:** complete
**Created:** 2026-09-08
**Original request:** see `original_prompts.md` entry to be appended by the documenter for 2026-09-08. Full verbatim text reproduced below since the documenter has not run yet at plan-creation time.

> Simplify the recipe create/edit form (apps/web/templates/pages/recipes/form.php, backed by RecipeController.php + RecipeService.php + RecipeRepository.php), plus two small housekeeping cleanups. Requirements:
>
> ## 1. Recipe form simplification
> a. Keep as-is: Name (text, required) + Category (select, from RecipeService::CATEGORIES).
> b. Description stays optional (already is on the backend — just make sure the UI doesn't visually imply it's required).
> c. Batch Size means the total finished-product volume the recipe yields (e.g. "20 L"), as opposed to Water Quantity (water actually used, since some is lost to boil-off/grain absorption). Keep the field but add a short inline hint/label clarifying this distinction so it's not confusing.
> d. Every "*_unit" field (batch_size_unit, water_unit, sugar_unit, yeast_unit, and each ingredient row's unit) must become a constrained selection (dropdown, or an icon-based picker if that reads better for units like L/gal/kg/g/oz) instead of a free-text input. Define a sensible fixed list of brewing units (volume: L, gal, mL, qt; weight: kg, g, lb, oz) — reuse the same list everywhere a "unit" applies rather than inventing different lists per field, unless a field genuinely needs a narrower subset (e.g. yeast quantity units are usually packet/g/mL, not liters).
> e. Every "*_type" field (sugar_type, yeast_type, ingredient_type) must become a dropdown of fixed values instead of free text. ingredient_type already has a constrained list (RecipeService::INGREDIENT_TYPES = fruit/grain/hop/other) driving the existing <select> — keep that. sugar_type and yeast_type currently have no constrained list; define reasonable fixed option sets (e.g. sugar_type: table sugar/dextrose/honey/DME/LME/other; yeast_type: ale/lager/wine/champagne/wild/other) and validate server-side the same way category/ingredient_type already are (invalid value silently falls back to a safe default, per the existing pattern in RecipeController::parseRecipeDataFromRequest / parseIngredientsFromRequest).
> f. Layout: group each quantity+its unit side by side as a compact row/section — one section for Batch Size + its unit, one for Water Quantity + its unit, one for Sugar Quantity + its unit + its type, one for Yeast Quantity + its unit + its type. Overall form should read as minimal, not a long vertical stack of individual labeled fields.
> g. target_og and target_fg: these are specific-gravity values stored as DECIMAL(6,3) (e.g. 1.050). Constrain the inputs to the 0.990–1.300 range (displayed/typed as thousandths, i.e. "990 to 1300" the user mentioned means this range in gravity-point terms — use whatever concrete input representation reads best, e.g. step 0.001 min 0.990 max 1.300, or an integer 990-1300 UI that maps to /1000 under the hood — your call, but validate the range both client- and server-side). Additionally, the OG field must show a "fancy" live-updating estimated potential ABV as the user types (standard homebrew formula: ABV% ≈ (OG − FG) × 131.25 when FG is present, otherwise show potential/max ABV assuming full attenuation to FG 1.000). This needs a small vanilla-JS progressive enhancement — no framework (see note below).
> h. Ingredient rows: each ingredient's fields (name, type, quantity, unit, timing note) already render in one fieldset/row — keep that shape but reduce the default visible rows from the current MIN_INGREDIENT_ROWS=6 down to 3, and add an "Add ingredient" button that appends another blank row client-side (vanilla JS, no framework — the current form.php docblock notes this app deliberately avoids a JS framework/add-remove-row widget "per the plan's don't-over-engineer guidance"; a small unobtrusive JS enhancement for this one interaction is fine and necessary now, but keep it minimal and keep the no-blank-rows-submitted server-side behavior that already exists).
>
> Relevant files already located: apps/web/templates/pages/recipes/form.php, apps/web/src/Recipes/RecipeController.php (validation + parsing), apps/web/src/Recipes/RecipeService.php (CATEGORIES/INGREDIENT_TYPES constants), apps/web/src/Recipes/RecipeRepository.php. Check apps/web/docs and /docs (data-model.md, business-logic.md) for existing conventions before adding new constants/migrations if the unit/type lists need DB-level constraints.
>
> ## 2. Remove TO_BE_DONE.md
> It's currently tracked in git (`git ls-files` shows apps root TO_BE_DONE.md) even though .gitignore already has a `TO_BE_DONE.md` line in it (that line was apparently added without ever untracking the file — git status is otherwise clean). Delete the file from the working tree and `git rm --cached` it (or equivalent) so it's actually untracked going forward, keeping the existing .gitignore entry.
>
> ## 3. Move the deploy script to a root-level bin/
> Currently at apps/web/bin/deploy.sh (apps/web/bin/migrate.php stays where it is — only the deploy script moves). Move it to a new /bin/deploy.sh at the repository root. Check what apps/web/deploy.conf / apps/web/deploy.conf.example and the script itself assume about relative paths (working directory, path to apps/web tree, path to its own config file) and fix those references so the script still works correctly when invoked from the new root bin/ location (invoked from repo root, per the docs/plans/0003-v1.0.2-deploy-tooling.md context). Update README.md / CHANGELOG.md / docs/plans references to the script's old path if any exist.
>
> Do a version bump and CHANGELOG entry consistent with this repo's existing release conventions (see recent CHANGELOG.md entries and docs/plans/*.md for the pattern).

## Summary of analyser report

Full report was returned inline by the analyser agent. Key findings/decisions carried into this plan:

- **Grounding:** `/docs` is the ground truth; there is no `apps/web/docs` directory. Confirmed by direct inspection: `apps/web/templates/pages/recipes/form.php` currently renders every `*_unit`/`*_type` field (except `category`/`ingredient_type`) as a free-text `<input type="text">`. `RecipeController::MIN_INGREDIENT_ROWS` is currently 6. `RecipeService::CATEGORIES`/`INGREDIENT_TYPES` are the only existing constrained-value constants; `sugar_type`/`yeast_type`/the five `*_unit` columns have no constant/validation today. `target_og`/`target_fg` are plain `<input type="text">` with zero range validation anywhere (`nullableNumeric()` casts blindly, no bounds check). Baseline suite: 369 tests / 676 assertions, 85.19% classes / 97.53% methods / 99.14% lines.
- **Factual correction to the request (Part 2):** `TO_BE_DONE.md` is **already untracked**. `git ls-files | grep -i to_be_done` returns nothing; `git status --ignored` already lists it under ignored files; `git log --follow -- TO_BE_DONE.md` shows zero history in this repo's 3-commit history. The request's premise ("currently tracked in git") does not match reality — re-verified directly by the coordinator, confirmed. This is a verify-only task, not a fix.
- **Business impact:** Recipe creators get a shorter, less error-prone form (closed unit/type choices instead of freeform text) and a live ABV estimate. One real, product-visible tradeoff: existing free-text `yeast_type`/`sugar_type` values that aren't strain names but arbitrary text (e.g. test fixture `yeast_type = 'US-05'`) can't be represented in the new closed dropdown — re-saving such a recipe through the edit form will not be able to preserve a value outside the fixed list. This is an intentional, user-specified tradeoff, not an oversight; flagged for visibility, not blocking. Parts 2/3 have zero end-user-facing impact (repo hygiene / ops tooling only), consistent with how 1.0.2/1.0.3 CHANGELOG entries frame similar changes.
- **Architectural impact:** This introduces the **first client-side JavaScript in the app** — a new `apps/web/public/js/recipe-form.js`, plain vanilla JS, no framework, no build step, loaded via a plain `<script src>` only from the recipe form template. `docs/architecture.md`'s current "no client-side JavaScript" wording needs a small correction to stay accurate (still: no framework, no build step, one narrowly-scoped enhancement script). No new services/routes/repositories. **DB-level constraints decision:** app-layer only for `sugar_type`/`yeast_type`/the `*_unit` columns — no new migration, no DB `ENUM`. Rationale: these are nullable `VARCHAR` columns (unlike `category`/`ingredient_type`, which are `NOT NULL DEFAULT` `ENUM`s), a "unit" value applies across 5 columns in 2 tables with genuinely different valid subsets, and this is scoped as a UX/validation simplification, not a schema-integrity project. **target_og/target_fg representation:** plain `<input type="number" step="0.001" min="0.990" max="1.300">` mapped 1:1 onto the stored `DECIMAL(6,3)` — simpler than an integer 990–1300 UI with a `/1000` JS conversion layer, and gets free browser-level validation as a first line of defense (still backed by required server-side validation). **Deploy script relocation:** today `SCRIPT_DIR` = `apps/web/bin`, so `APP_ROOT="$SCRIPT_DIR/.."` = `apps/web` (correct — this is what `stage_release()` copies via `cp -a "$APP_ROOT/." "$staging_dir/"`, and where `deploy.conf`/`deploy.conf.example` live). After the move to `/bin/deploy.sh`, the same computation would wrongly resolve `APP_ROOT` to the repo root. Fix: compute a `REPO_ROOT` from `SCRIPT_DIR/..`, then set `APP_ROOT="$REPO_ROOT/apps/web"` explicitly, keeping `deploy.conf`/`deploy.conf.example` and the staged source exactly where they are today. The `usage()` help text's config-location line also needs rewording (it currently implies the config lives in the script's own parent directory, which stops being true once the script moves).
- **Code impact:** `RecipeService.php` gains `UNITS`, `YEAST_UNITS`, `SUGAR_TYPES`, `YEAST_TYPES`, `TARGET_GRAVITY_MIN`/`MAX` constants. `RecipeController.php` gets new validation/fallback branches in `parseRecipeDataFromRequest()`/`parseIngredientsFromRequest()` (fallback to `null` for the nullable `*_unit`/`sugar_type`/`yeast_type` fields — not a magic non-null default, since these columns are nullable, unlike `category`), new range checks in `validateRecipe()` for `target_og`/`target_fg`, and `MIN_INGREDIENT_ROWS` 6→3. `templates/pages/recipes/form.php` is rewritten (same file) to use `<select>`s everywhere, add the hint text, group fields into compact rows, add the OG/FG number inputs + ABV output element, and include the new JS. New `apps/web/public/js/recipe-form.js` (add-row + live ABV). Small `apps/web/public/css/app.css` addition for compact row layout + hint styling. `RecipeRepository.php` needs no change (generic column mapper). No migration files touched.
- **Testing impact:** Existing `RecipeControllerTest.php`/`RecipeServiceTest.php` give a solid pattern to extend (`testCreateWithInvalidCategoryFallsBackToOther` / `testCreateWithInvalidIngredientTypeFallsBackToOther`). New tests needed: invalid value → null fallback for each new constrained field; OG/FG boundary tests (0.990 and 1.300 inclusive-accepted, 0.989/1.301 rejected with 422 + message, non-numeric rejected); `MIN_INGREDIENT_ROWS`=3 rendering test (create form shows exactly 3 blank rows; edit form with >3 existing ingredients still renders all of them, no truncation — `buildIngredientRows()`'s pad-up-only logic should already be safe, but deserves an explicit regression test given the constant changes). Existing `RecipeRepositoryTest.php` fixtures that use out-of-list free text (e.g. `yeast_type => 'US-05'`) call the repository directly, bypassing controller validation, and are unaffected. `public/js/recipe-form.js` has no PHPUnit path (no JS tooling anywhere in this repo) — verify manually (documented transcript: add-row button works, ABV figure updates live for a couple of OG/FG combinations, form still fully submits with JS disabled), mirroring the existing `bin/deploy.sh` non-PHPUnit-coverage precedent in `docs/test-suites.md`. Template rewrite gets structural PHPUnit assertions (new `<select>`/option markup present) plus a manual visual check. Coverage target: ≥85% on all touched PHP code, no regression below the 369/676 baseline.
- **Ambiguities resolved by the coordinator (documented, not re-asked):**
  1. TO_BE_DONE.md's premise is already satisfied — verify-only task (T9), not a fix.
  2. DB-level ENUM constraints for the new lists: app-layer only, no migration (design call within the latitude the request explicitly gave).
  3. Version number: **1.0.4**, following this repo's established pattern of incrementing the patch component regardless of scope shape across all three prior releases (1.0.1, 1.0.2, 1.0.3), rather than switching to semver-minor now.
