## Summary of analyser report

Full report was returned inline by the analyser agent (not written to a separate file this round). Key decisions carried into this plan:

- **Grounding:** `/docs/*.md` are fully written and accurate (not placeholders); root `README.md`/`CHANGELOG.md` exist with a 1.0.1 entry; `apps/web/composer.json` is currently `"version": "1.0.1"`. No deploy-related file exists anywhere in the repo yet. `apps/web/bin/migrate.php` is the only existing CLI entry point and is **forward-only** — there is no `down()`/rollback migration mechanism anywhere in the codebase. `ssh`/`sftp`/`scp`/`rsync`/`curl` are available locally; `sshpass` is not installed by default but is installable (`apt`); `lftp`/`expect`/`shellcheck` are not installed.
- **Business impact:** this is a pure ops/release-engineering change — no application/user-facing behavior changes. It automates 3 of the README's existing 6 manual deploy steps (upload code, `composer install --no-dev`, run `bin/migrate.php`); DB creation, first-time `.env` setup, and pointing the document root at `apps/web/public` remain one-time, host-console-dependent, manual steps that cannot be safely generalized to "any shared host." Password-based SSH/SFTP (as explicitly requested) is a weaker posture than key-based auth; the README must say so plainly once and explain why password auth is the supported baseline here. Migrations being forward-only means **automatic rollback can only ever cover the uploaded code**, never an already-applied schema change — the README's rollback documentation must not imply otherwise.
- **Architectural impact:** new artifact type for this repo — an ops script that lives in the repo but is never executed by the app and never uploaded to the deployed host. `apps/web/bin/deploy.sh`: dependency-light bash + OpenSSH `ssh`/`sftp` clients + `sshpass` (required for non-interactive password auth — bare OpenSSH cannot do this from a non-TTY) + `tar`/`mv` remote-side. `rsync` was considered and rejected as the *primary* transfer mechanism (requires `rsync` installed remotely, not guaranteed on a generic shared host); `lftp` rejected as an added dependency with no real benefit over `sftp -b` batch mode. No second language runtime — matches the project's zero-Node/zero-JS-build-step footprint. New gitignored `apps/web/deploy.conf` + committed `apps/web/deploy.conf.example` template, same pattern as `.env`/`.env.example`. One new line in `apps/web/.gitignore`.
- **Safest ordering (adopted):** (1) build a local staging copy of `apps/web` excluding dev-only/secret paths, run `composer install --no-dev --optimize-autoloader` **inside that staging copy** (not the dev working tree) — local composer, not remote, is the default, to avoid depending on remote Composer availability/PHP-CLI-version match and to keep the remote side's responsibilities minimal; (2) back up the existing remote release directory (`mv` to a timestamped name) before touching it; (3) upload the staged code via SFTP batch mode into a fresh remote directory; (4) run `bin/migrate.php` remotely over SSH against the **remote's own pre-existing `.env`** (never uploaded, never overwritten); (5) optional HTTP health check, with automatic rollback (swap the backup directory back) on failure. Reasoning: back up before overwrite, upload before migrate (code must be in place before the migration runner file exists to run), migrate before declaring success, health-check last as the final gate.
- **Config file shape (`apps/web/deploy.conf.example`, `KEY=VALUE`, `.env.example`-style comments):** `DEPLOY_HOST`, `DEPLOY_PORT`, `DEPLOY_SSH_USER`, `DEPLOY_SSH_PASS`, `DEPLOY_SFTP_USER` (usually same as SSH user, override only if the host issues separate SFTP-only credentials), `DEPLOY_SFTP_PASS`, `DEPLOY_REMOTE_PATH` (remote dir whose `public/` subdir is the document root), `DEPLOY_REMOTE_PHP_BIN` (default `php`), `DEPLOY_BACKUP_KEEP` (retention count), `DEPLOY_HEALTHCHECK_URL` (optional, enables auto-rollback). Deliberately no remote-composer keys — local staging is the default for 1.0.2.
- **Upload excludes:** `.git`, `vendor/` (the dev-installed one — composer runs fresh in the staging copy), `.env*`, `tests/`, `docker*`/`docker/`, `deploy.conf`, `phpunit.xml.dist`, `.phpunit.result.cache`, `build/`, and any local deploy logs. Never uploading `deploy.conf`/`.env*` is the single highest-risk failure mode in this whole task (leaking credentials onto the deployed host, or clobbering a working production `.env`) and needs an explicit verification step, not just an exclude-list entry trusted on faith.
- **Testing impact (no PHPUnit coverage percentage applies to a bash script):** `bash -n` syntax check (mandatory); `shellcheck` if available at implementation time (check again, don't assume absent); a real `--dry-run` mode that performs zero network activity and prints the full action plan; end-to-end verification against a throwaway local SSH+MySQL test target (Docker `openssh-server` container, mirroring the project's existing Docker-for-MySQL-testing pattern) covering: a real upload+migrate run, a second consecutive run (backup-and-redeploy idempotency), a forced-failure run proving automatic rollback restores the prior release, an explicit check that no `deploy.conf`/`.env*` file ever appears in the uploaded remote tree, and a password containing `$`/space to catch quoting bugs. Record these runs' outcomes in the implementer's task notes as the "done when" evidence for this artifact, in place of a coverage number.
- **README:** add a new subsection immediately after the existing "Deployment on generic PHP/MySQL shared hosting" section (e.g. "### Automated redeploys with `bin/deploy.sh`"), explicitly framed as automating steps 1/2/5 of the existing 6-step manual list while steps 3/4/6 remain manual — cross-reference, don't duplicate or contradict.
- **Version/changelog:** routine — bump `apps/web/composer.json` to `1.0.2`, add a `## 1.0.2` entry to `CHANGELOG.md` above the `## 1.0.1` entry in the same style, explicitly noting no application/user-facing behavior changed this release.
