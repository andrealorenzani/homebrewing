## Summary of analyser report

Full report is reproduced in `docs/plans/0002-analyser-report.md`. Key decisions carried into this plan:

- `/docs` (architecture/business-logic/code-structure/data-model/test-suites) are still placeholder stubs; only `apps/web/` scaffold (composer.json, phpunit harness, empty dirs) from T1 of the v1.0.0 plan actually exists. Everything else in this plan is new code, not a resumption of partial work.
- v1.0.1 requires building the load-bearing minimum of the original v1.0.0 foundation — router/front-controller/CSRF, view renderer + plain CSS, DB layer + migrations (6 tables, not 7 — `rate_limit_events` dropped), session auth/login (no antispam), recipe CRUD, batch+diary CRUD — before layering the four new items on top. This is a fresh, renumbered task list (V1-V11), not a resumption of `0001-v1.0.0-initial-release.md`'s T-numbers.
- **Explicitly out of scope for v1.0.1** (deliberate, not an oversight): sharing tokens/QR codes, admin area, antispam/rate-limiting, the ornate "parchment/journal" diary CSS theme, a "browse all public content" page. None of these are load-bearing for items 1-4.
- **Visibility model:** `is_public` boolean column (`NOT NULL DEFAULT 0`, i.e. private by default) added directly to `recipes` and `batches` in their initial migration — no later ALTER needed since no schema has ever been applied live. Enforcement is at read time in the service layer: owner always full access; other authenticated users and anonymous visitors get view-only access if-and-only-if `is_public`, else a 404 (not a 403 — don't reveal existence of private resources). No share-token concept exists in v1.0.1, so "not viewable via public/share links" has no separate mechanism to violate; noted as a forward-looking non-goal, not built now.
- **New architectural piece not in the original T2 design:** an "optional auth" request resolver (attaches the current user if a session exists, without forcing a redirect/login), used by view routes that must serve both owners and public visitors, distinct from the existing "auth required" guard used by create/edit/delete/toggle routes.
- **Homepage:** card grid of the N (config-driven, default 6) most-recently-updated **public** recipes only, each with name, category, and a link to the read-only detail view. Graceful empty state when there are zero public recipes. No equivalent showcase for diaries (not requested).
- **Nav:** top-level "Recipes" and "Diaries" links, each routing to that domain's own-listing view (the logged-in user's own recipes / own batches).
- **DB environment:** no host MySQL/MariaDB credentials are reachable non-interactively (confirmed 2026-09-06 — `sudo mysql` needs an interactive TTY password not available in this session). Docker is available locally with `mysql:8.0` and `php:8.3-cli` images already cached (the latter was used in T1 of the 0001 plan to work around missing host PHP extensions `mbstring`/`dom`/`xmlwriter`/`curl` — re-verify at the start of V1 whether that's still needed rather than assuming it's since been fixed on the host). DB provisioning for this plan means a **Dockerized `mysql:8.0` instance** for both dev and integration-test databases, not host-level provisioning.
- **Testing:** fake/in-memory `Db` double for unit tests (Router/Config/renderer/migration-runner control flow — easily ≥85%), Dockerized MySQL for integration tests (Auth/Recipes/Batches repository behavior, ownership/visibility branches). The visibility enforcement matrix — {owner, other authenticated user, anonymous} × {public, private} × {view, edit, delete, homepage listing} — is the single highest-risk area and needs deliberate, explicit test cases, not incidental coverage.
- README is deliberately the second-to-last task so it documents what's actually built, not aspirational scope; must not describe sharing/QR/admin as if they exist.
