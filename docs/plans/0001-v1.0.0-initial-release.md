## Summary of analyser report

Full report is reproduced in `docs/plans/0001-analyser-report.md`. Key decisions carried into this plan:

- Server-rendered PHP 8.3 app, no framework. Composer for dependency management (`chillerlan/php-qrcode` runtime, `phpunit/phpunit` dev-only). Native PHP sessions for auth.
- App code lives under `apps/web/` (`public/`, `src/`, `templates/`, `db/migrations/`, `bin/migrate.php`, `tests/`).
- "Brewing session" renamed to **Batch**; its diary is made of **batch log entries**.
- Data model: `users`, `rate_limit_events`, `recipes`, `recipe_ingredients`, `batches`, `batch_log_entries`, `schema_migrations`.
- Sharing: opaque per-resource tokens on `recipes` and `batches`, independent of each other; unauthenticated read-only public views; QR rendered on demand via `chillerlan/php-qrcode` (SVG, no GD needed).
- Antispam: honeypot + simple server-side challenge + DB-backed rate limiting (`rate_limit_events`), no third-party keys.
- Known v1 limitations (explicitly accepted, not oversights): no email verification, no password-reset flow, antispam is a deterrent not a hard guarantee.
- CSRF protection is in scope as foundational/non-negotiable even though not explicitly requested, since the app has session-based state-changing forms.
- Testing: PHPUnit, ≥85% coverage on touched PHP code per task. Coverage doesn't meaningfully apply to the parchment CSS itself (T11) — glue code touched there still needs ≥85%.
- Tasks are split so Phase A (T1–T4) needs no live database; Phase B (T5–T12) does.
